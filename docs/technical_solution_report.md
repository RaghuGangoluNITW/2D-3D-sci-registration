# Technical Solution Report: 2D–3D X-ray/CT Spine Registration Pipeline

**Scope:** architecture and configuration of the registration pipeline as implemented in this repository; root-cause comparison of public-dataset success vs. real-patient (JYOTHI) failure; concrete action items to close each gap.

**Repo root:** `mslevel_reg/` (git: no commits yet, working tree only — see §6).
**Numbers policy:** every number below is cited to the file it was read from. Where a number could not be found in code/logs, it is marked **not found in repo**.

---

## 1. Executive Summary

The system estimates the 3D pose of a lumbar spine CT relative to a 2D C-arm X-ray by detecting vertebra (and pedicle) landmarks in the X-ray with a CNN, solving an initial camera pose via PnP/EPnP from 3D CT ↔ 2D X-ray point correspondences, then refining that pose by maximizing Gradient-Orientation (GO) image similarity between a bank of CT-rendered DRRs and the real X-ray, using multi-start CMA-ES/Nelder-Mead optimization. On the public DeepFluoro pelvis dataset (real cadaveric fluoroscopy) the pipeline reaches **4.3mm** PDE (source: `POC/src/deepfluoro_multiview_log3.txt`, pair 036+045, k=2). On the public VerSe lumbar-spine CT, using **synthetic DRR targets** (not real X-ray), it reaches **0.32mm** PDE (source: `POC/src/verse_multiview_log.txt`). On the real patient JYOTHI it reaches **79.4mm** (blind, raw unlabeled frames) or **1.01mm** only if the camera pose is seeded directly from doctor-labeled frames, a sanity check rather than an automatic result (source: `POC/src/jyothi_calibrated_log.txt`). The bottom-line root cause is three compounding, independent gaps: (1) JYOTHI's AP landmarks (3 points, L3–L5) are far more collinear than DeepFluoro's 14 bilateral pelvis landmarks, making PnP ill-conditioned; (2) JYOTHI has no independent C-arm geometry calibration (DeepFluoro's poses were derived offline from an independent 2020 annotation, JYOTHI's camera model is an assumed/default config, not a measured one); and (3) the CNN landmark detector trained for JYOTHI has only moderate accuracy on the real AP frame (PCK@10mm=0.444) and is effectively unusable on the real LAT frame (PCK@10mm=0.083), because training data is dominated by synthetic DRRs with very few matching real images.

## 2. Solution Architecture — Step by Step Pipeline

Processing order, each stage's purpose, architecture, and implementing file(s):

### 2.1 CT loading and 3D landmark extraction
- **Purpose:** load the pre-op CT volume and the doctor-labeled 3D vertebra centroids (D12, L1–L5), optionally augmented with auto-extracted pedicle points.
- **Implementation:** `src/generic_patient_loader.py` (`GenericPatientLoader.load()`), reading `CT label/<ct>.nrrd` + `CENTROID.mrk.json` (Slicer markup JSON, LPS mm). For DeepFluoro: `src/deepfluoro_loader.py` loads CT + 14 pelvis landmarks directly from the dataset's HDF5 file (`ipcai_2020_full_res_data.h5`).
- **Pedicle augmentation:** `scripts/extract_transverse_process_tips.py` thresholds CT at `BONE_HU_THRESHOLD = 250.0` HU, searches a local box of half-width `LOCAL_BOX_MM = 30.0` mm around each centroid, and picks the most lateral bone voxel on each side subject to `MIN_TIP_DIST_MM = 8.0` and `MAX_TIP_DIST_MM = 42.0` mm from the centroid (source: `scripts/extract_transverse_process_tips.py`). This is pure HU-thresholding + local-axis PCA search — no trained model, no TotalSegmentator (TotalSegmentator could not be installed; `pip install` failed on a `dipy` build error, per the auto-pedicle POC script's docstring, `POC/src/run_jyothi_auto_pedicle_poc.py`). Output is written to `EXTRA_LANDMARKS.mrk.json` and merged into `landmarks_3d` by `generic_patient_loader.py`.

### 2.2 Synthetic DRR generation (training data and registration bank)
- **Purpose:** render digitally-reconstructed radiographs from the CT at known poses, with free 2D landmark labels, for (a) training the CNN landmark detector and (b) building the candidate-pose "bank" scored during registration.
- **Implementation:** `scripts/generate_synthetic_drrs.py` using the GPU ray-caster in `src/deepfluoro_drr.py` (`DeepFluoroDRR.generate_from_extrinsic`, Beer-Lambert line-integral over a 5D grid-sampled attenuation volume).
- **Exact configuration (JYOTHI batch, source: `mslevel_reg/regen_with_pedicles_log.txt`):** patients `['BIKNA','JYOTHI','RASVANTI','SARKHI','SHRILATHA','SHRINIVAS','Swaroop']`; `n_per_view = 1000`; render resolution `RENDER_SIZE = 256` px → saved at `SAVE_SIZE = 512` px (source: `scripts/generate_synthetic_drrs.py` constants); HU threshold `150.0` (default `--hu_threshold`, source: `scripts/generate_synthetic_drrs.py` argparse default and confirmed in the log); ray-marching `N_STEPS = 200` (source: `scripts/generate_synthetic_drrs.py`, with an explicit comment that `n_steps=80` produced noise/stripe artifacts on CTs with >450 Z-slices); pose perturbation ranges `ROT_RANGE_DEG = 25.0`°, `TRANS_RANGE_MM = 50.0` mm around seed poses; quality filters `MIN_VISIBLE_LM = 3`, `MIN_BONE_COVER = 0.05`, `MIN_MARGIN_PX = 30`.

### 2.3 CycleGAN domain style-transfer (real X-ray → DRR domain)
- **Purpose:** translate real intraoperative X-rays toward the synthetic-DRR visual domain to reduce train/test domain gap for the downstream landmark detector.
- **Architecture (source: `src/cyclegan.py`):** `UNetGenerator` with `ngf=32` base filters, 3 downsampling stages (`e1`→`e2`→`e3`, channel progression `1→32→64→128`), a bottleneck of `n_res=4` `ResBlock`s at `ngf*4=128` channels, and a 3-stage decoder with skip connections, output mapped from `tanh` to `[0,1]`. `PatchDiscriminator` ("70×70 PatchGAN") with `ndf=32`: 4 conv layers (`1→32→64→128→1`), stride-2 for the first three, LSGAN (MSE) adversarial loss. Loss terms: adversarial (LSGAN) + cycle-consistency (`lambda_cycle=10.0` default) + identity (`lambda_ident=5.0` default) — standard Zhu et al. 2017 CycleGAN formulation. An `ImageBuffer` (history size 50) stabilizes discriminator training.
- **Training hyperparameters (source: `scripts/train_cyclegan.py` argparse defaults, confirmed against `train_cyclegan_v3_log.txt`):** `--epochs 150` default, `--lr 2e-4`, `--size 256` (`TRAIN_SIZE=256`), `--ngf 32`, `--ndf 32`, `--n_res 4`, batch size 1 (hardcoded in `DataLoader(..., batch_size=1, ...)`), mixed precision (`torch.amp.GradScaler`) on CUDA, Adam optimizer `betas=(0.5, 0.999)`, linear LR decay after `epochs//2`. Domain A (real X-ray) = 69 labeled NRRD images + up to 701 extra unlabeled real C-arm/X-ray frames (from `data/extra_xrays_manifest.csv`, built by `scripts/extract_extra_xrays.py`); Domain B (synthetic DRR) = up to 11,294 PNGs (source: `train_cyclegan_v3_log.txt`: "XRayDataset: 69 labeled... 701 extra... 770 total... DRRDataset: 11294 synthetic DRRs"; an earlier run `train_cyclegan_v2_log.txt` used only 5,745 DRRs with no extra X-rays).
- **Current usage status:** `scripts/train_landmark_detector.py`'s own LOPO training runs for the pedicle-augmented AP/LAT detectors used **zero** converted-X-ray rows ("converted=0", source: `mslevel_reg/train_landmark_pedicles_ap_log.txt`), i.e. the CycleGAN step exists and trains, but was not feeding the final heatmap-detector training runs analyzed in this report.

### 2.4 2D landmark/pedicle heatmap detection on real X-ray
- **Purpose:** given a real (or synthetic) X-ray, predict pixel locations of up to 18 landmark classes (6 vertebra centroids + 12 bilateral pedicle points).
- **Architecture — `LandmarkHeatmapNet` (source: `src/landmark_model.py`):** encoder = `timm.create_model('mobilenetv3_small_100', pretrained=True, in_chans=1, features_only=True, out_indices=(0,1,2,3,4))`, i.e. MobileNetV3-Small adapted to 1-channel input, 5 feature levels at strides 2/4/8/16/32. Decoder: 4 `UpBlock`s (`ConvTranspose2d` ×2 upsample + skip concat + two `ConvBnRelu` + `Dropout2d`), channel path `576→128→64→32→32`, with `dropout=0.3` in training (`dropout=0.0` at inference per `landmark_detector.py`). Head: one independent 2-layer conv head per class (`Conv2d(32,16,3)→ReLU→Conv2d(16,1,1)`) rather than a single shared 1×1 projection — the file states this is to "prevent channel collapse". Output: `(B, NUM_CLASSES, 128, 128)` raw logits from `(B, 1, 512, 512)` input. Docstring claims ~1.5M total trainable params (vs 5.6M for an EfficientNet-B0 alternative).
- **Loss — `HeatmapLoss` (source: `src/landmark_model.py`):** weighted MSE on sigmoid-activated predictions vs. Gaussian-blob ground truth, `pos_weight = 100.0` (training call explicitly sets `HeatmapLoss(pos_weight=100.0)`), `threshold = 0.01` for deciding "positive" pixels, with optional per-channel `valid_mask` to zero out loss for vertebrae not labeled in a given sample.
- **Dataset constants (source: `src/landmark_dataset.py`):** `CLASS_NAMES` = 18 entries (`D12, L1..L5` + `<LEVEL>_LEFT_PED/_RIGHT_PED` for `D12,L1..L5`); `NUM_CLASSES = 18`; `IMG_SIZE = 512`; `HMAP_SIZE = 128` (1/4 of input); `SIGMA_PX = 16` px Gaussian sigma for heatmap targets (comment: "~16px = ~26mm at orig scale... critical for generalization with <60 training images"). CLAHE normalization (`clipLimit=2.0, tileGridSize=(8,8)`) applied to both DRRs and real X-rays before training/inference, intended to reduce the DRR/X-ray appearance gap.
- **Training loop (source: `scripts/train_landmark_detector.py`):** LOPO (leave-one-patient-out) over all patients in the manifest. Defaults: `--epochs 200`, `--batch 4`, `--lr 3e-4`, optimizer `AdamW(weight_decay=1e-4)`, LR schedule = linear warmup over `10%` of epochs then cosine decay to a floor of `0.01×`. Early-stopping `patience = 50` epochs (no improvement in best validation mean-mm error). Backbone freeze rule: parameters in `blocks.0`, `conv_stem`, or `bn1` are frozen (`requires_grad_(False)`); all later backbone blocks + decoder train. Augmentation (`_augment` in both `landmark_dataset.py` and `train_landmark_detector.py`): intensity jitter (`alpha∈[0.6,1.5]`, `beta∈[-0.2,0.2]`), gamma `∈[0.6,1.8]`, Gaussian blur (`p=0.4`, kernel ∈{3,5,7}), Gaussian noise (`σ∈[0,0.06]`), rotation `±15°`, scale `[0.80,1.20]`, translation `±5%` of image size, horizontal flip `p=0.5`; the training-script variant additionally applies a 30%-probability rectangular cutout (simulating metal/occlusion). Per-epoch training set capped at `max_per_epoch=1500` rows (all real rows + a random sample of synthetic/converted rows up to the cap), with an `oversample = max(1, 200 // len(train_rows))` factor applied on top. Checkpoint selection criterion is lowest validation **mean mm error**, not PCK@10mm (explicit code comment: with few training images PCK@10mm "is too tight to move off 0.000 for many epochs... would freeze checkpoint selection at epoch 1").
- **Pixel-to-mm conversion constant:** `PIXEL_MM = 0.2` mm/px, hardcoded in `scripts/train_landmark_detector.py`, `scripts/train_ssm_regressor.py`, `scripts/eval_ssm_regressor.py` (matches the Ziehm Vision FD camera config's `pixel_spacing_mm`, see §3).
- **Inference wrapper (source: `src/landmark_detector.py`):** `LandmarkDetector.predict()` runs the CNN, extracts per-channel argmax peaks above `DEFAULT_CONF = 0.05`, then (optionally) hands partial detections to a `SpineSSM.fit_and_complete()` call that fits a 5-mode Statistical Shape Model to fill in any undetected vertebrae from the learned anatomical prior.

### 2.5 Statistical Shape Model (SSM) regressor — alternative/companion path
- **Purpose:** directly regress 8 abstract shape parameters (5 PCA shape coefficients + tx/ty centroid + log-scale) instead of per-pixel heatmaps, and separately, complete/snap partial landmark detections onto a learned anatomically-valid manifold.
- **SSM construction (source: `src/spine_ssm.py`):** `SpineSSM.build_from_manifest()` builds a `12`-dim shape vector (`D12,L1..L5` × 2D) from all real + BUU samples with ≥2 valid vertebrae, EM-PCA imputation (10 iterations) for missing vertebrae, final PCA kept to `n_modes = 5` (CLI default `--n_modes 5`).
- **`SSMRegressor` architecture (source: `src/ssm_regressor.py`):** backbone default `resnet50` (2048-dim features, 1-channel adapted, ImageNet-pretrained) with a legacy `mobilenetv3_small_100` (576-dim) option. MLP head for ResNet-50: `2048→512→256→128→8` with `LayerNorm`+`ReLU`+`Dropout` between layers (dropout default `0.3`), final-layer weights/bias zero-initialized. Loss: weighted MSE, weights `w_shape=1.0, w_pos=3.0, w_scale=1.5` (`SSMRegressionLoss`).
- **Training (source: `scripts/train_ssm_regressor.py`):** LOPO, `PIXEL_MM = 0.2`, manifest default `data/landmark_manifest_combined.csv` (not found on disk currently, see §6).

### 2.6 Patient-specific pose regressor — third, independent path (not cross-patient)
- **Purpose:** bypass EPnP entirely by regressing the full 6-DOF camera pose directly from the image, trained per-patient on that patient's own synthetic DRRs (each DRR already carries its exact generating pose).
- **Architecture (source: `src/pose_regressor.py`):** backbone `resnet34` (default, timm, 1-channel), head `feat_dim→256→128→9` (LayerNorm+ReLU+Dropout). Output = 9-D: 6-D continuous rotation representation (Zhou et al. CVPR 2019, Gram-Schmidt-decoded to a rotation matrix) + 3-D translation normalized by measured ranges `TRANS_MM_MIN=[-2000,-2000,-1000]`, `TRANS_MM_MAX=[2000,2000,3200]` mm. Loss `PoseRegressionLoss` upweights the depth (z-translation) term by `depth_weight=2.0` because monocular depth is explicitly called out as the hardest-to-learn quantity.
- **Status for JYOTHI (source: `e2e_jyothi_posereg_v3_log.txt`):** checkpoint reports `val_pde=32.5mm, synthetic-only` — i.e. this path's own internal validation (on synthetic data) is already far from the <2mm target, and its real-frame end-to-end PDE in the same log is 47–104mm (FAIL on every tested frame).

### 2.7 3D–2D correspondence and PnP/EPnP initial pose
- **Purpose:** given N≥3 matched 3D CT landmarks and 2D X-ray detections, solve an initial 6-DOF camera pose.
- **Implementation (source: `src/generic_patient_loader.py`, `_solve_pnp`):** `cv2.solvePnP` with `cv2.SOLVEPNP_SQPNP` when exactly 3 correspondences are available, `cv2.SOLVEPNP_EPNP` for ≥4. Falls back to a heuristic "anatomy pose" (camera placed at a fixed azimuth from the landmark centroid) if PnP fails or <3 correspondences exist (`_anatomy_pose`).

### 2.8 DRR bank generation around the initial pose
- **Purpose:** render many candidate-pose DRRs in a neighborhood of the initial pose, as GO-scoring candidates for retrieval/refinement.
- **Implementation:** `POC/src/run_jyothi_auto_pedicle_poc.py` / `run_jyothi_calibrated_multiview.py` build banks of `N_PER=200` entries per view (400 total) by perturbing the seed camera source position with `rng.normal(0, 20.0, 3)` mm jitter and re-aiming at the landmark centroid.

### 2.9 GO (Gradient-Orientation) similarity scoring/refinement
- **Formula (source: `src/similarity.py`, `gradient_orientation_similarity`):** images are Gaussian-smoothed with `sigma` (default `2.0`, used as `sigma=2.0` throughout the POC scripts), gradients computed by central differences, pixels kept where both DRR and X-ray gradient magnitude exceed their own median (`t_drr`, `t_rad`), angular difference wrapped to `[0, π/2]`, weight `w_i = (2/π)·ln(|θ_i|+1)`, `GO_cost = Σw_i / max(N, N_LB)` with `N_LB = 0.30 × total_pixel_count` (`n_lb_frac=0.30`). The code's own in-line comments flag that this weight formulation is ambiguous as written in the source paper (gives 0 weight at perfect alignment) and the implementation normalizes it into a similarity in `[0,1]` as a best-effort interpretation; the file cites "Ketcha 2017" as the source formula. A separate `go_cost()` wraps this as `1 - similarity` with a coverage guard (returns worst cost `1.0` if DRR nonzero-pixel fraction `<0.15`).
- **Related metrics also implemented in the same file (NGF, edge-NCC, MI, LNCC, multiscale-NCC, gradient-NCC, NMI, entropy-of-difference, correlation-ratio, stochastic-rank-correlation, gradient-difference, pattern-intensity):** present as alternative/combinable cost functions (e.g. `fast_combined_cost` blends NGF `0.6` weight + edge-NCC `0.4` weight), but the actual JYOTHI/DeepFluoro/VerSe POC run scripts read in this investigation all call `gradient_orientation_similarity` directly, not the combined cost.
- **Optimizer (source: `src/optimizer.py`):** `multistart_cmaes()` implements Ketcha 2017 §2.3: Phase 1 = `n_starts` (paper default 50 for Stage 1) independent CMA-ES runs from kD-tree-partitioned initial points (`kdtree_multistart_init`), weak tolerance `tolx_phase1=1.0`, population `popsize=125` (Stage-1 paper value); Phase 2 = single tight-tolerance (`tolx_phase2=0.1`) re-optimization of the Phase-1 best, search range divided by 4. Per-stage search ranges (Table 1 of the cited paper, hardcoded as `SR_STAGE1..4`): Stage 1 `[60,60,50,15,15,10]` (mm/mm/mm/deg/deg/deg), Stage 2 `[30,30,20,10,10,7]`, Stage 3 `[15,15,10,7,7,5]`, Stage 4 `[10,10,10,5,5,5]`. **However**, none of the JYOTHI/DeepFluoro/VerSe POC scripts actually call this CMA-ES module — they all use `scipy.optimize.minimize(method='Nelder-Mead')` with their own simplex/step/bounds setup (confirmed by reading `run_jyothi_auto_pedicle_poc.py`, `run_jyothi_calibrated_multiview.py`, `run_deepfluoro_multiview_test.py`, `run_verse_multiview_test.py` — all import `scipy.optimize.minimize`, none import `src/optimizer.py`). `src/optimizer.py`'s CMA-ES multi-start framework exists in the repo but is not the code path that produced the 4.3mm/0.32mm/79.4mm numbers in this report.

### 2.10 Final estimated pose / PDE metric
- **PDE (Projection Distance Error)** is computed uniformly across all tests as the mean Euclidean pixel distance (converted to mm via the relevant pixel spacing) between landmarks projected at the estimated pose and their ground-truth 2D positions, restricted to landmarks visible in-frame. See `src/deepfluoro_loader.py` (`compute_pde_for_pose`), `src/generic_patient_loader.py` (`compute_pde`), and the per-test scripts' own `pde_mm`/`pde_at_delta` helper functions.

## 4. Why It Works on Public Datasets vs. Fails on the Real Dataset

| Factor | DeepFluoro (pelvis, real X-ray) | VerSe (spine, synthetic X-ray) | JYOTHI (spine, real X-ray) |
|---|---|---|---|
| Landmark count & spread (PCA collinearity ratio) | 14 bilateral points, ratio **0.72** — well-conditioned PnP (`load_deepfluoro.py`) | 5 centroids, ratio **0.186** — poorly conditioned, but moot because single-view PnP is never the pose source here (pose comes from the known synthetic rendering pose, retrieval/refinement only) | 3 AP landmarks (L3-L5), ratio **0.128–0.129** — nearly a straight line, the worst of the three, and the single real driver of EPnP instability |
| Camera geometry calibration | Independently derived once (2020, by the dataset's original researchers) via EPnP from an independent annotation; stored and reused, never re-derived from the test X-ray itself | Not applicable — pose is read directly from the known DRR-rendering camera parameters (no real camera at all) | No independent calibration exists. The pipeline uses either (a) the generic `ziehm_vision_fd.json` default config (SID=1110mm, 0.2mm/px) which is **not** the actual DICOM-reported machine geometry (SID=1050mm, 0.288mm/px per `carm_dicom_dump.txt`), or (b) a one-off PnP solve from the same 3-collinear-point AP labels that are themselves degenerate |
| Real training/test images available | 14 (eval) real fluoroscopy projections for a specimen with calibrated poses, used purely for retrieval scoring, no CNN trained | 0 real images (synthetic-only test) | 32 real AP images across all patients combined (29 per JYOTHI-held-out fold); only 1 fold checkpoint (`fold_JYOTHI.pth`) exists for LAT |
| Domain gap (synthetic DRR ↔ real X-ray) | Present but tolerated — GO similarity used directly on real fluoroscopy without a trained CNN detector in the loop | Zero — synthetic DRR compared against synthetic DRR, by design, to isolate pipeline geometry from domain gap | Present and compounded with low real-image count: landmark CNN trained on 7213 synthetic AP rows vs. only 29-32 real AP rows, and 0 converted (CycleGAN-adapted) rows in the actual training run |
| Soft tissue / metal / instrument noise | Cadaveric specimens — generally no live surgical instruments | Not applicable (synthetic only) | Real intraoperative frames contain surgical instruments (K-wires, needles); `metal_suppression.py` exists and reduces this but a residual gradient-noise floor was still measured (AP GO SNR≈1.03–1.04, LAT≈1.03) |
| Ground-truth validation availability | Independent, pre-existing 2020 annotation never touched by the pipeline being tested | Exact (rendering is ground truth by construction) | Only the doctor-labeled AP/LAT sets provide any 2D ground truth, and the AP ground truth is itself the degenerate 3-point case |
| Numeric result | **4.3mm** (multiview, real X-ray) | **0.32mm** (multiview, synthetic X-ray) | **79.4mm** (blind automatic) / 1.01mm (only when seeded from the same degenerate labeled pose — not an independent result) |

**Direct explanation of the gap the user asked about:** pelvis-on-real (4.3mm) beats spine-on-real (79.4mm) for two independent reasons that both have to be true simultaneously for success: (1) pelvis landmarks are naturally non-collinear (0.72 vs 0.128 ratio) so PnP/retrieval starts from a geometrically sound neighborhood even without perfect calibration; (2) DeepFluoro's camera geometry was independently, offline-calibrated once and never re-derived from degenerate points, whereas JYOTHI's calibration is either a generic default (`ziehm_vision_fd.json`) that does not match the DICOM-reported real values, or a pose recovered from the same collinear 3-point AP set that is the geometry problem in the first place. Spine-on-synthetic (0.32mm) is not evidence the geometry pipeline is broken — it proves the retrieval+refinement *math* is correct when there is no domain gap and the true pose is reachable from the bank; it does not and cannot address either the collinearity problem or the calibration problem, both of which only manifest with real geometry.

## 5. Action Items to Close Each Gap

For every gap in §4, stated separately as "ask a person" vs. "derive from existing repo files":

1. **C-arm SID/SOD/pixel-spacing mismatch (`ziehm_vision_fd.json` vs. actual machine).**
   - *Derive ourselves first:* the real DICOM header for JYOTHI's C-arm already contains `(0018,1110) Distance Source to Detector = 1050` and private tag `(0019,1014)/(0019,1213) = 0.288mm` pixel spacing — both already extracted and used correctly inside `POC/src/run_jyothi_auto_pedicle_poc.py` and `run_jyothi_calibrated_multiview.py` (`SDD_MM=1050.0, PIX_MM=0.288`). The production pipeline config (`configs/cameras/ziehm_vision_fd.json`, SID=1110mm, pix=0.2mm/px) does **not** match this and should be corrected or a new per-machine config file added. This is a same-file fix, no new data needed — check `carm_dicom_dump.txt` and `carm_geom_dump.txt` for every frame, since the exact SID can vary by exposure (the dump already shows one row with "1050" for every captured frame value, so it appears constant for this session but should be re-verified per session rather than assumed).
   - *Ask a person only if* the dumped DICOM tags are themselves found to be placeholder/default values rather than true per-exposure measurements (Ziehm firmware sometimes reports a fixed nominal SID). If so, ask the hospital's radiology physicist or Ziehm field engineer: "does this C-arm report true measured source-to-detector distance per exposure, or a fixed nominal value — and can you provide/perform a calibration-phantom shot to verify?"

2. **Unknown C-arm isocenter position in CT world coordinates (not just direction).**
   - *Derive ourselves first:* `carm_geom_dump.txt` only has positioner angles (primary/secondary) per frame, which give camera **direction**, not **position** relative to the CT. The current pipeline infers position only via PnP on the (degenerate) 3-point AP labels. There is nothing else already in the repo that supplies this — it cannot be derived from existing files.
   - *Ask a person:* ask the hospital physicist/radiographer to perform (once per machine, not per patient) a calibration-phantom acquisition — image a phantom of known geometry (e.g. a precisely-dimensioned grid or ball-bearing fiducial array) at a known table/C-arm relative position, and record the resulting image. This is exactly how DeepFluoro's offline calibration was obtained (per `src/deepfluoro_loader.py`'s description of EPnP-from-independent-annotation) and is the single highest-value real-world data acquisition this project could ask for.

3. **AP landmark collinearity (3 points, ratio 0.128).**
   - *Derive ourselves first:* `scripts/extract_transverse_process_tips.py` already auto-extracts 12 pedicle 3D points from the existing CT with no new doctor input, improving the 3D collinearity ratio to 0.417 (`POC/src/jyothi_auto_pedicle_log.txt`). This is already implemented and already run for JYOTHI. The remaining gap is that these auto-pedicle 3D points have **no matching reliable 2D detection** in the real X-ray (the LAT pedicle CNN detector's PCK@10mm is 0.083 — see checkpoint data above) — so the fix must target item 4 below, not re-derive more 3D points.
   - *Ask a person only if* the auto-pedicle extraction needs validation: ask a radiologist to visually confirm (one-time, on the existing CT, ~5 minutes) that the auto-extracted `EXTRA_LANDMARKS.mrk.json` points actually land on left/right pedicles and not on ribs or the adjacent vertebra, per the explicit caveat already written into `extract_transverse_process_tips.py`'s own docstring ("must be spot-checked visually... could land on rib, adjacent vertebra, or other bone").

4. **CNN landmark detector accuracy on real X-ray is low (AP PCK@10mm=0.444, LAT PCK@10mm=0.083).**
   - *Derive ourselves first:* the training run that produced these checkpoints used **zero** converted (CycleGAN-adapted) X-ray rows (`converted=0` in `train_landmark_pedicles_ap_log.txt`) despite the CycleGAN stage (`scripts/convert_xrays_to_drr.py`, `src/cyclegan.py`) already being implemented and already trained (`checkpoints/cyclegan/` outputs referenced in `train_cyclegan_v2_log.txt`/`v3_log.txt`). Re-running `scripts/convert_xrays_to_drr.py` to regenerate `data/converted_xray_manifest_ap.csv`/`_lat.csv` and re-training `scripts/train_landmark_detector.py` with those rows included (as the script already supports via `--converted_manifest`) is a config/data-pipeline fix, not new data collection — assuming the manifests and raw patient folders can first be restored (see §6).
   - *Ask a person:* this gap cannot be fully closed by data engineering alone — ask the surgical/radiology team whether additional AP and LAT X-ray frames (ideally from different patients/sessions, with manual 2D vertebra+pedicle labeling, ~2 minutes/image per the project's own README benchmark) can be collected and labeled to grow the real-image training pool beyond the current ~29-36 images per view; this is the single most direct lever on PCK accuracy given the stated "<60 training images" constraint already noted in the code (`landmark_dataset.py` comment on `SIGMA_PX`).

5. **Metal/instrument gradient noise on real frames.**
   - *Derive ourselves first:* `src/metal_suppression.py` already implements both a blind percentile-threshold method (`suppress_metal`) and a DRR-guided method (`suppress_metal_drr`); confirm the registration scripts are calling the DRR-guided variant (more targeted) rather than the blind one, which is a code-path check, not new data.
   - *Ask a person:* not required for this item; it is solvable within the repo.
